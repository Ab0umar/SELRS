# Accounting UI anti-slop audit 002

**Date:** 2026-10-03  
**Mode:** AFTER, session override  
**Scope:** Entire routed accounting module, shared accounting primitives, responsive styles, accounting entry workflows, reports, print preview, and routed prototypes.  
**Method:** Read-only source audit using `antislop`, `antislop-ui`, `antislop-layoutmobile`, `antislop-human`, `antislop-copywriting`, and `antislop-code`. The audit was fanned out across cohesive accounting surfaces and reduced into one deduplicated findings list.  
**Product code changed:** No.

## Executive summary

The accounting module has a strong baseline: most data views expose loading, error, empty, and retry states; routes are protected; navigation permissions have focused tests; mobile and desktop presentations are intentionally separated in many screens; and most copy is concrete Arabic accounting language rather than generic marketing text.

The remaining risk is concentrated in **data-entry integrity, responsive table containment, keyboard semantics, incomplete recovery paths, and duplicated workflow implementations**. The highest-priority issues are incorrect or ambiguous accounting entries, invalid import dates, capped inquiry results with no pagination, mobile focus failures, nested interactive controls in loan rows, and missing print/report behavior for patient accounts.

This report is source-based. Runtime/browser visual inspection, contrast computation, end-to-end keyboard/touch testing, print output checks, and fresh build/test execution were not performed as part of this audit.

## Findings

### F-001 HIGH: Accounting home derives Today from UTC

- **Rule:** R-27, sourced metrics must use the user’s accounting day.
- **Evidence:** `client/src/features/accounting/AccountingHome.tsx:96` uses `new Date().toISOString().split("T")[0]` and passes that date to `dashboardSummary` and `transactions` at `:98-108`. The shared accounting contracts accept a date-only filter.
- **Impact:** Outside UTC, daily revenue, receipt counts, and activity can be assigned to the wrong accounting day around midnight.
- **Suggested fix:** Derive the date in the configured clinic or user timezone, or pass an explicit timezone and office-day boundary consistently to both queries.

### F-002 HIGH: Accounting entry forms accept zero, invalid, or two-sided transactions

- **Rule:** R-27, accounting data-entry integrity.
- **Evidence:** `AccEntryDrawer.tsx:89-94`, `AccountingHomeFund.tsx:101-107`, `AccountingInstapay.tsx:105-112`, `AccountingLedger.tsx:109-113`, and `AccountingDrSaadany.tsx:96-100` normalize input with `parseFloat(...) || 0` or permit both sides without submit-time validation. Controls mainly declare `min=0` or disable only for missing required fields.
- **Impact:** Users can create 0/0 rows, negative or non-finite values, or simultaneous income and expense entries, producing ambiguous balances and unreliable history.
- **Suggested fix:** Validate finite positive amounts before mutation, require exactly one populated side where that is the ledger invariant, reject negatives and 0/0, and show field-associated Arabic errors.

### F-003 HIGH: Import parser accepts syntactically shaped but impossible dates

- **Rule:** R-27, import data integrity.
- **Evidence:** `client/src/features/accounting/accImportParse.ts:88-95` accepts `YYYY-MM-DD` and `DD/MM/YYYY` matches without calendar-range validation. `parseAccSheet` emits `txDate` at `:155-158`; fallback `Date` parsing is runtime-dependent.
- **Impact:** Values such as `2025-99-40` can become ledger movements, corrupting sorting, filtering, and accounting history.
- **Suggested fix:** Apply strict month/day and leap-year validation, reject impossible dates, and expose the invalid-date count and reason in the preview.

### F-004 HIGH: Receipt inquiry hard-caps results at 500 without pagination

- **Rule:** R-27, accounting result completeness.
- **Evidence:** `AccountingPatientsInquiry.tsx:93` defaults `limit` to 500 and `:510-514` only warns when `rows.length >= 500`. There is no total, `hasMore` metadata, next/previous control, or load-more flow.
- **Impact:** A valid query with more than 500 receipts cannot be fully reviewed, leaving omitted accounting records inaccessible from the surface.
- **Suggested fix:** Add server-supported cursor or offset pagination with total or `hasMore` metadata and accessible controls. Keep the truncation notice as secondary context.

### F-005 HIGH: Receipt inquiry clips the table at tablet widths

- **Rule:** R-03 and R-35, responsive overflow must not clip accounting data.
- **Evidence:** `AccountingOpReport.module.css:29-38` sets `.reportBlock { overflow: hidden; }`; `:56-76` keeps a nine-column `nowrap` table; stacked reflow starts only at `max-width: 640px`. The inquiry has no contained intermediate scroll state.
- **Impact:** At small-tablet and narrow-window widths, columns and click targets can be clipped before mobile reflow begins.
- **Suggested fix:** Move the reflow breakpoint to the actual content failure width or add an accessible intermediate horizontal-scroll container. Do not conceal overflow.

### F-006 HIGH: Raw accounting form controls lose focus indication below 1024px

- **Rule:** R-32 and R-34, every interactive control needs a visible focus indicator.
- **Evidence:** `AccountingLedger.tsx:169-170` and `AccountingServiceEntry.tsx:135-136` apply `outline-none`. `accounting-web.css:1-6` and `:236-237` provide replacement focus rules only inside `min-width: 1024px`, scoped through an ancestor class not present on the section markup.
- **Impact:** Keyboard users on phones and narrow tablets can move through accounting fields without a visible location indicator.
- **Suggested fix:** Provide an unconditional accounting-scoped `:focus-visible` replacement or remove `outline-none`, then verify below 1024px and at 200% zoom.

### F-007 HIGH: Loan register rows contain nested buttons

- **Rule:** R-32, interactive semantics must not nest conflicting controls.
- **Evidence:** `AccountingLoans.tsx:559-624` renders mobile `div role="button"` rows containing a delete button. `:774-803` repeats the pattern with `tr role="button"` and nested delete controls at `:850-885`.
- **Impact:** Assistive technology receives a button-like row containing another button, creating conflicting announcements and activation behavior and obscuring table semantics.
- **Suggested fix:** Use an explicit edit button or link per record, or a non-interactive row container, with delete as a sibling control and one clear keyboard target for editing.

### F-008 HIGH: Several accounting touch controls are below the mobile target minimum

- **Rule:** R-03 and R-35, interactive targets need about 44 by 44 pixels.
- **Evidence:** `AccountingAdvances.tsx:798-809` has an un-sized search clear button, `:1057-1072` uses `h-9 w-9`, and `:374-392` uses short employee options. Similar undersized controls appear in `AccountingHomeFund.tsx:323-334`, `:187-195`, `:584-602`; `AccountingInstapay.tsx:329-340`, `:590-604`; `AccEntityImportDialog.tsx` sheet toggles; `AccountingDrSaadany.tsx:181-187`, `:314-325`; and `AccountingLoans.tsx:858-870`.
- **Impact:** Thumb users can miss or accidentally activate dense clear, cancel, pagination, option, sheet, and confirmation controls.
- **Suggested fix:** Give each local accounting control a minimum 44 by 44 pixel hit box with adequate gaps while keeping icons visually small. Do not rely on the shared primitive to enlarge a fixed-width child.

### F-009 HIGH: Dr Saadany date sort is mouse-only

- **Rule:** R-32 and R-03, sorting must be keyboard-operable and expose state.
- **Evidence:** `AccountingDrSaadany.tsx:422-435` puts `onClick` on the sortable `th` without `tabIndex`, keyboard handling, a button, or `aria-sort`; only the visual arrow changes.
- **Impact:** Keyboard and assistive-technology users cannot trigger or understand the current date sort direction.
- **Suggested fix:** Use a focused native button or keyboard-operable header control, add `aria-sort`, and preserve a visible focus style.

### F-010 HIGH: Accounting prototypes collapse query states into zeros and a blank table

- **Rule:** R-27 and C-4, loading, empty, and error states must be explicit and perceivable.
- **Evidence:** `AccountingPrototypes.tsx:542-558` starts three queries but does not branch on loading, error, or data state. Metrics format missing values as zero at `:185`, `:194`, `:203`, `:219`, `:441`, `:449`, and `:457`. `ActivityTable` maps rows without state handling at `:282-327`.
- **Impact:** Slow, failed, or genuinely empty responses look like valid zero activity, so users cannot distinguish unavailable data from no records.
- **Suggested fix:** Branch each query into announced loading, useful empty, and retryable error states. Never substitute numeric zero for unavailable data.

### F-011 HIGH: Patient account has no wired print or report action

- **Rule:** R-27, report behavior must be wired to the accounting surface.
- **Evidence:** `PatientAccount.tsx:9` imports `AccountingOpReport.module.css`, but `:132-520` renders no print control, `printScope`, `noPrint` class, or `body.print-daily-revenue` mode required by `AccountingOpReport.module.css:218-267`.
- **Impact:** Users cannot intentionally print or export the patient account, and normal browser print does not receive the shared report scoping behavior.
- **Suggested fix:** Add a keyboard-operable print action, wrap printable content in the accounting print scope, hide controls using the existing convention, and verify the summary plus tables.

### F-012 MEDIUM: Accounting module title and description are silently discarded

### F-013 MEDIUM: Cashbook-only failure triggers a generic summary error

- **Rule:** R-27, errors must identify the failing surface and preserve trustworthy data.

- **Impact:** A cashbook failure can present the whole dashboard as failed even when displayed metrics remain valid, without telling users which data is stale or repaired.
- **Suggested fix:** Scope error copy and retry controls to the failing query, or keep cashbook error handling with the cashbook and sync status instead of gating summary cards.

### F-014 MEDIUM: Activity header presents a page length as today’s receipt total

- **Rule:** R-27, status counts must match their stated scope.
- **Evidence:** `AccountingHome.tsx:106-116` requests `limit: 20` and stores the returned page. `:345-350` renders `receipts.length` as `إيصال` without saying it is a capped/latest page or using a server total.
- **Impact:** When more than 20 receipts exist, the header can imply a complete daily count while showing only the loaded page.
- **Suggested fix:** Label the value as latest or displayed receipts, or return and render a server-side total.

### F-015 MEDIUM: Sync or push failure has no in-context retry

- **Rule:** R-32, failed actions need an accessible recovery path.
- **Evidence:** `AccountingHome.tsx:126-152` stores `syncResult` and a toast on mutation failure. `:274-294` renders the result alert/log with no retry button, so recovery requires finding the original action at `:231-260`.
- **Impact:** Keyboard and screen-reader users receive failure feedback but no obvious recovery control, and the original action context can be lost.
- **Suggested fix:** Store the failed mode and render a labelled retry action in the alert, preserving pending and disabled behavior.

### F-016 MEDIUM: Import sheet selection is visual-only to assistive technology

- **Rule:** R-34, selected state must be communicated programmatically.
- **Evidence:** `AccEntityImportDialog.tsx:184-201` renders sheet toggles as buttons whose selected styling changes at `:193-197`, but there is no `aria-pressed` or explicit accessible group label.
- **Impact:** Keyboard users can operate the toggles, but screen readers do not announce which sheets are included in the import.
- **Suggested fix:** Expose `aria-pressed` for each toggle and provide an explicit accessible group name explaining the selected import scope.

### F-017 MEDIUM: Expense filter changes show stale rows without an updating announcement

- **Rule:** R-27 and C-4, refresh state must be perceivable.
- **Evidence:** `AccountingExpenses.tsx:44-47` keeps `placeholderData(previous)` and `:89` sets `aria-busy` from `isFetching`, but the only visible loading branch at `:158-164` checks `isLoading`, which is false during refetch.
- **Impact:** After changing filters, users continue reading the previous rows and totals without a visible indication that they are being replaced.
- **Suggested fix:** Add a concise `role=status` updating message tied to `isFetching`, or replace rows with a loading state during filter changes and keep totals synchronized.

### F-018 MEDIUM: Mobile expense cards expose unlabeled values

- **Rule:** R-32 and C-4, responsive data needs meaningful structure.
- **Evidence:** `AccountingExpenses.tsx:173-191` renders date, notes, and amount as generic `div`s. Unlike desktop headers at `:202-210`, mobile markup has no field labels or `dl/dt/dd` structure.
- **Impact:** Screen-reader users must infer that the final number is the expense amount, and color alone does not provide the missing semantic label.
- **Suggested fix:** Use a semantic record structure or explicit Arabic labels for date, description, and expense amount.

### F-019 LOW: Expense-category filter group is unlabeled

- **Rule:** R-32, grouped controls need an accessible name.
- **Evidence:** `AccountingExpenses.tsx:92-94` labels the year group with a fieldset and legend, but `:115-135` renders category buttons in a plain `div` without a group label.

### F-020 MEDIUM: Ledger and service-entry invalid submissions are silently ignored

- **Rule:** R-27 and C-4, validation must be perceivable and actionable.
- **Evidence:** `AccountingLedger.tsx:109-113` returns when date or amount invariants fail. `AccountingServiceEntry.tsx:93-98` returns when date, patient code, or service is missing. Operation errors at later lines cover mutation failures only, while submit buttons merely disable.
- **Impact:** Users can be unable to save without being told which field needs correction, particularly when pressing Enter or encountering a disabled submit control.
- **Suggested fix:** Track local validation errors, associate them with controls using `aria-invalid` and `aria-describedby`, and state the exact Arabic rule before mutation.

### F-021 MEDIUM: Empty ledger navigation appears actionable but does nothing

- **Rule:** R-27, data views need an explicit empty state.
- **Evidence:** `AccountingLedger.tsx:397-410` wraps loading and error only. When `navigatorQ` succeeds with an empty array, navigation buttons still render at `:161-168` and `goTo` silently returns at `:157-160`.
- **Impact:** A first-time or cleared ledger gives no explanation of the empty state and leaves four apparently actionable controls with no effect.
- **Suggested fix:** Explain that there are no previous entries and disable or omit navigation controls until a row exists.

### F-022 MEDIUM: Advances and loans registers do not distinguish no matches from no records

- **Rule:** R-27, filtered data views need a distinct no-results state and recovery.
- **Evidence:** `AccountingAdvances.tsx:826-829` and `:971-979`, plus `AccountingLoans.tsx:554-557` and `:764-772`, use a generic empty message even when search is non-empty. Search state and clear controls exist nearby.
- **Impact:** Users cannot tell whether the register is genuinely empty or the current filter matched nothing, nor are they given clear recovery guidance.
- **Suggested fix:** Branch on active search, show a no-match message, and provide a clearly labelled clear-search action. Reserve the empty-register message for unfiltered data.

### F-023 MEDIUM: Space activation on mobile accounting rows can scroll and diverges from desktop

- **Rule:** R-32, keyboard activation must match click behavior.
- **Evidence:** `AccountingAdvances.tsx:553-559`, `AccountingLoans.tsx:574-583`, `AccountingHomeFund.tsx:359-361`, `AccountingInstapay.tsx:360-367`, and `AccountingDrSaadany.tsx:344-352` handle Enter or Space without consistently calling `preventDefault`; equivalent desktop handlers prevent it in several cases.
- **Impact:** Keyboard and switch users can select a row and also scroll, or receive different reset, focus, and scroll behavior than touch users.
- **Suggested fix:** Centralize row activation, call `preventDefault` for Space, and make click and keyboard paths perform the same reset, focus, and scroll behavior.

### F-024 MEDIUM: Editable and receipt rows reimplement button behavior on non-native elements

- **Rule:** R-32, use semantic controls for keyboard interaction.
- **Evidence:** `AccountingAdvances.tsx:535-559` and `:648-671` use `div` or `tr` with `role=button`, `tabIndex`, and custom handlers. Patient inquiry desktop rows at `:441-453` use tabIndex, click, and keyboard handling without `role=button`, while mobile receipts use real buttons.
- **Impact:** Announcement, activation, Space handling, disabled state, and focus semantics can diverge across repeated row implementations and break table expectations.
- **Suggested fix:** Use a native link or button inside each record, or one accounting-scoped row-control abstraction with explicit naming and consistent keyboard behavior.

### F-025 MEDIUM: Loan-entry workflows expose different fields and acceptance rules

### F-026 MEDIUM: Loan drawer save and delete failures can become no-ops

### F-027 MEDIUM: Loan edit affordance is hover-only on desktop

### F-028 MEDIUM: Home-fund and Instapay delete implementations are unreachable

### F-029 MEDIUM: Home-fund and Instapay add flows clear the form without a success announcement

### F-030 MEDIUM: Dr Saadany mobile running balance is an unlabeled color-coded number

### F-031 MEDIUM: Dr Saadany displays legitimate zero values as unavailable

### F-032 MEDIUM: Date-range errors are detached in doctor and patient account searches

### F-045 MEDIUM: Prototype paid-versus-outstanding status is color-only

- **Rule:** R-34 and C-4, status must not be communicated by color alone.
- **Evidence:** `AccountingPrototypes.tsx:317-323` assigns `text-success` or `text-warning` based on remaining but renders no status text, icon, or pattern. Metrics at `:189-205` likewise use color treatment without an explicit state label.
- **Impact:** Color-blind and low-vision users cannot reliably distinguish paid from outstanding rows or metrics, including in forced-colors mode.
- **Suggested fix:** Render explicit `مدفوع` or `متبقٍ` text, optionally with an icon, and keep color as secondary reinforcement.

### F-046 LOW: Prototype warning backgrounds use malformed double-opacity utilities

- **Rule:** R-01, utility classes must produce the intended visual hierarchy.
- **Evidence:** `AccountingPrototypes.tsx:198` and `:376` use `bg-warning/10/80` and `bg-warning/10/70`, which are not standard single-slash Tailwind opacity utilities.
- **Impact:** The amber surface treatment may be dropped while border and text styling remain, making comparison variants visually inconsistent.
- **Suggested fix:** Use a valid project-supported opacity class or explicit arbitrary color alpha and verify compiled output in both themes.

### F-047 LOW: Repeated structural and decorative comments add no rationale

- **Rule:** R-31, comments must add non-obvious information.
- **Evidence:** Obvious labels and markers appear in `AccEntryDrawer.tsx` at `:142`, `:160`, `:163`, `:179`, `:219`, `:238`, and `:254`; `AccountingAdvances.tsx` at `:42`, `:246`, `:515`, `:532`, and `:627`; `HomeFund.tsx:290`; `Instapay.tsx:296`; `DrSaadany.tsx:285`; and `layout-refined-add-filter` markers in `LasikRevenue.tsx:537`, `LasikServices.tsx:67`, and `LasikCost.tsx:140`.
- **Impact:** Comment noise makes real business-rule and browser-constraint notes harder to find and leaves process residue in accounting code.
- **Suggested fix:** Remove only generic, structural, and decorative comments. Retain rationale-bearing parser, print, focus, protocol, and business-rule comments.

### F-048 LOW: Decorative icons in labelled controls are not explicitly hidden

- **Rule:** R-34, decorative icons must not add accessible-name noise.
- **Evidence:** `AccountingHome.tsx:212-215`, `:238-244`, and `:253-259` place `RefreshCw` in text-labelled buttons without `aria-hidden`. `PrintPreview.tsx:400-410` similarly places `ArrowLeft` and `Printer` in labelled buttons without `aria-hidden`.
- **Impact:** Assistive technology may announce redundant or unlabeled SVG graphics in addition to visible control text.
- **Suggested fix:** Set `aria-hidden=true` on these decorative icons and retain visible text as the accessible name.

### F-049 LOW: Accounting launchpad description exposes backend jargon

- **Rule:** R-02, copy should name the user-visible job, not internal terminology.
- **Evidence:** `AccountingHome.tsx:38-42` labels a destination `استعلام الإيصالات` but describes it as `البحث عن رؤوس الإيصالات`.
- **Impact:** `رؤوس الإيصالات` is an implementation or data-model term and does not clearly describe the user task.
- **Suggested fix:** Use task language such as `البحث في الإيصالات وعرض تفاصيلها` if that matches the destination scope.

### F-050 LOW: Loan summary and receipt detail overuse coloured pills and elevated rounded cards

- **Rule:** R-05, R-11, and R-12, visual hierarchy should distinguish primary content from supporting surfaces.
- **Evidence:** `AccountingLoans.tsx:311-313` uses an unlabeled `N اسم` pill alongside multiple tinted monetary tiles at `:353-379` and `:627-667`. `ReceiptDetail.tsx:366-413` and `:464-529` repeat `rounded-2xl shadow-sm` with nested `rounded-xl` surfaces.
- **Impact:** Repeated accents, radius, and elevation flatten hierarchy and make counts, monetary concepts, context tiles, and line data compete for attention.
- **Suggested fix:** Reserve stronger accent and elevation for primary content, make supporting counts plainly labelled, and flatten or reduce radius and shadow on nested accounting surfaces.

### F-051 LOW: Receipt inquiry truncation warning contains a wording error

- **Rule:** R-02, copy must be precise and natural.
- **Evidence:** `ReceiptsInquiry.tsx:623-626` displays `قد تكون النتائج مقطوعة. اضيق نطاق البحث للحصول على نتائج أدق.` The imperative is misspelled or malformed.
- **Impact:** The only warning about incomplete accounting results loses clarity and trust.
- **Suggested fix:** Use precise reviewed Arabic wording such as `قد تكون النتائج مقطوعة. ضيّق نطاق البحث للحصول على نتائج أدق.`

### F-052 LOW: Prototype route renders the same live activity table three times

- **Rule:** R-14 and R-05, repeated content must earn its space and reflect hierarchy.
- **Evidence:** `AccountingPrototypes.tsx:602-632` passes identical `summary`, `cashbook`, and `rows` into all three `PrototypePanel` instances; each panel renders `ActivityTable` at `:462`.
- **Impact:** Users scan repeated accounting rows instead of seeing the actual layout differences, making the comparison long and visually noisy.
- **Suggested fix:** Use one shared table with switchable treatments, or make each comparison a compact structural preview and show one full table for the selected direction.

### F-053 LOW: Prototype screen claims live or real rows without state-qualified explanation

- **Rule:** R-36 and C-5, copy should state concrete truth rather than unsupported assurance.
- **Evidence:** `AccountingPrototypes.tsx:570` labels the screen `بيانات حية` and `:249-251` says `صفوف فعلية، بدون حشو بصري`, while query state handling is absent at `:542-558` and possibly empty rows are rendered three times.
- **Impact:** During loading, error, or empty conditions the copy overstates what users are seeing and makes a prototype sound more production-complete than the evidence supports.
- **Suggested fix:** Show live-data claims only after successful queries and use neutral descriptive copy alongside explicit loading, empty, and error states.

### F-054 LOW: Accounting stylesheet duplicates the same desktop media-query wrapper

- **Rule:** R-31, duplicated shared CSS patterns should have one authoritative implementation.
- **Evidence:** `accounting-web.css:1-244` and `:245-296` are separate identical `@media screen and (min-width:1024px)` blocks.
- **Impact:** The split wrapper makes breakpoint behavior harder to audit and increases the chance that future accounting-wide rules are added to the wrong block.
- **Suggested fix:** Merge the blocks or separate them by documented concern while keeping base and mobile accessibility rules unconditional.

## Strengths observed

- Accounting routes and launchpad destinations are wired to existing accounting routes, and the module is protected and wrapped in `AccountingShell`.
- Most audited data views expose explicit loading, error, empty, and retry states through `AccountingQueryBoundary` or local branches.
- Accounting navigation permission filtering has focused tests covering unavailable permissions, empty groups, child-only access, tokenized permissions, and order.
- `OperationalModuleShell` provides a skip link, content landmark, labelled navigation and select controls, and responsive metric layout.
- Cashbook filters distinguish filtered-empty from genuinely empty data, reset pagination on filter changes, use labelled notes search, and provide keyboard-scrollable desktop table regions plus mobile cards.
- Entry drawers use explicit labels and ids, controlled Sheet/Dialog primitives, focus restoration, Arabic close labels, and confirmation for destructive deletion.
- Import supports xlsx/xls selection, parse feedback, bounded preview, ignored-row counts, a 2,000-row guard, and a real preview table with headings.
- Expenses, advances, loans, Instapay, home-fund, doctor, patient, receipt, daily-revenue, and Lasik surfaces generally provide intentional mobile/desktop alternatives rather than only shrinking one desktop table.
- Common filter, pagination, refresh, reset, and action controls usually have Arabic labels, disabled boundary states, visible focus utilities, and approximately 44px sizing where the shared primitive is used.
- Receipt detail has guarded print behavior with an explicit payload and loading/error/missing-header/empty-line checks. Daily revenue and Lasik print flows include no-print scoping and mobile PDF or preview fallbacks.
- Tables commonly use semantic `thead`, `tbody`, and `th scope="col"` markup, accessible overflow regions, `aria-sort` on several working sort controls, and deliberate mobile card representations.
- Reviewed copy is predominantly concrete Arabic accounting language with no fabricated statistics, marketing buzzwords, emoji decoration, or generic CTA claims in the audited surfaces.
