# SELRS UI anti-slop audit 013

**Mode:** AFTER, session override  
**Scope:** public login, authenticated app shell, `/home`, `/today` (redirects to `/bookings`), `/workflow`, `/patient-hub`, and `/accounting`  
**Date:** 2026-10-03

## Method and boundaries

This is a read-only runtime and source audit. No product source files were changed.

- Product direction: `DESIGN.md`, especially the Arabic-first RTL clinical workspace, task-focused composition, mobile containment, and accessible states.
- Runtime URL: `http://localhost:4000`.
- Authentication: the user supplied local test credentials in chat; they were used only against this local app and are not repeated in this report.
- Browser runtime: the repository's installed Puppeteer package with the installed Microsoft Edge executable, because the dedicated in-app browser connector was unavailable on this device.
- Captures: `.work/previews/login-*.png`, `.work/previews/authenticated-*.png`, and `.work/previews/route-*.png`.
- Tested viewport sizes: 375x812, 768x1024, 1280x900, and 1920x1080 for login and the authenticated home; 375x812 and 1280x900 for the four operational routes.
- Runtime result: no horizontal page overflow was detected in the inspected states; 0 console errors and 0 failed network requests were recorded during the pass.
- `/today` redirected to `/bookings`; that resolved page was inspected as the today/booking surface.

Priority follows the anti-slop tiers: **HIGH** for Hard Gate rules, **MEDIUM** for Purpose-Gate or direction gaps, and **LOW** for Quality Locks.

## Findings

### 1. HIGH — Patient Hub has no informative first-use state and hides its page title

**Rules:** R-27, R-05, C-4; `DESIGN.md:72-81,103-105`

**Evidence:**

- At `/patient-hub`, both the 375px and 1280px captures show a large blank surface with only a back arrow and the search field. There is no visible page title or first-use explanation. See `route-patient-hub-mobile.png` and `route-patient-hub-desktop.png`.
- `client/src/pages/PatientHubShell.tsx:558-560` renders the no-patient heading as `<h1 className="sr-only">مركز المريض</h1>`, so the route has a semantic title but no visible orientation.
- `client/src/pages/PatientHubHome.tsx:207-250` renders recent patients only when `recent.length > 0`; there is no first-use branch for the common case where the recent list is empty.
- The search-result empty state exists at `PatientHubHome.tsx:160-165`, but it only appears after a search query. It does not explain the initial blank screen.

**Why it matters:** A staff member entering the module for the first time cannot tell whether the screen is intentionally waiting for a patient, whether data failed to load, or what the normal next action is. The blank header also weakens location awareness inside a dense clinical shell.

**Suggested fix after approval:** Show a visible `مركز المريض` heading in the no-patient header. Add a first-use state beneath the search field explaining that the user can search by patient name, code, or phone and then select a record. Keep the existing no-results and error states distinct from the first-use state.

### 2. HIGH — The mobile primary navigation is wider than the 375px viewport and clips item discoverability

**Rule:** R-03, Mobile Responsiveness

**Evidence:**

- The authenticated 375px capture shows the bottom navigation presenting more destinations than can fit in one resting view; the leftmost label is visibly partial. See `authenticated-mobile.png` and `route-accounting-mobile.png`.
- The runtime DOM exposes nine bottom-nav buttons plus `المزيد` at 375px for the inspected account. The navigation viewport is 375px wide while each tab uses `min-w-16` and the row uses `overflow-x-auto` in `client/src/components/layout/AppBottomNav.tsx:364-380,385-416`.
- The current design preserves page width, so this is not a document-level horizontal overflow defect. It is a navigation discoverability and reflow defect: a primary destination is partially hidden until the user horizontally scrolls the nav.

**Why it matters:** The bottom bar is the main route switcher on mobile. A partially visible label looks accidental and makes the first or last destination harder to discover and tap, especially for staff working one-handed at reception.

**Suggested fix after approval:** Keep a small, stable set of primary destinations visible without horizontal scrolling, and move the rest into `المزيد`. If role-specific navigation requires more items, use a clearly labelled secondary sheet rather than relying on a clipped horizontal row. Verify that the resting state shows complete labels at 375px and preserves 44px touch targets.

### 3. MEDIUM — The clinical workflow changes language and reading direction inside one task

**Rules:** R-02, R-31; `DESIGN.md:54-68,122-123`

**Evidence:**

- `client/src/pages/WorkflowPrototypeLive.tsx:2512-2547` wraps the live patient picker in `dir="ltr"` and renders the visible labels `Visit Date` and `Patient`.
- The same screen renders English runtime states at `WorkflowPrototypeLive.tsx:2562-2565`: `Loading…` and `No visits found.`
- The optional section action remains `Add Section` at `WorkflowPrototypeLive.tsx:3747-3752`.
- The mobile and desktop captures show the resulting mixed-language picker and section controls in an otherwise Arabic-first, RTL clinical workflow. See `route-workflow-mobile.png` and `route-workflow-desktop.png`.

**Why it matters:** Users scan an Arabic-first clinical screen with a stable RTL model, then encounter English labels and a left-to-right control group without an evident reason. The result is less predictable than the surrounding UI, and the user has to reinterpret the task language while entering clinical data.

**Suggested fix after approval:** Translate visible labels and loading/empty messages into Arabic. Limit `dir="ltr"` to the numeric or code fragments that need it, not the entire picker label group. Preserve machine-readable ISO values in state while presenting localized Arabic dates to the user.

## Verified strengths

- Login, home, bookings, workflow, patient hub, and accounting rendered at the inspected viewport sizes without document-level horizontal overflow.
- The login form has explicit username and password labels, a labelled password-visibility toggle, a 44px password toggle target, and 44px primary/portal actions.
- The shared design tokens provide a visible `:focus-visible` outline and 44px mobile control minimums in `client/src/styles/design-system.css:90-113`.
- The authenticated shell uses Arabic RTL at the document level and the inspected controls had real destinations or visible state changes in the captured routes.
- The runtime pass recorded no console errors or failed network requests.

## Delivery-gate status

This audit does **not** certify the full product. The following evidence was not completed in this pass:

- Measured WCAG contrast for every text, border, icon, and selected-state pairing in both themes.
- Full keyboard traversal of every inspected route, including modal Escape behavior and focus restoration.
- Dark-theme and print-route visual verification.
- On-screen keyboard behavior on a physical or emulated mobile device.
- Click-through of every control and all loading, empty, and error branches across the complete route inventory.

## Resolution

No findings were fixed in this turn. This is an AFTER-mode audit. Product changes should wait until the user approves specific finding numbers. Findings not approved should remain untouched.
