## Findings

### 1. HIGH — Visible accounting copy contains forbidden em dashes

**Rule:** R-02, Copywriting, Hard Gate

**Evidence:** Visible strings and fallback values contain the em dash character in multiple accounting screens, including:

- `client/src/features/accounting/AccEntityImportDialog.tsx:76,84,93`, in import validation and toast messages.
- `client/src/features/accounting/AccountingAdvances.tsx:349`, in an optional-field label.
- `client/src/features/accounting/PatientAccount.tsx:252,293`, in the patient summary and missing-value fallback.
- `client/src/features/accounting/AccountingHome.tsx:838,856`, in activity-feed fallbacks.
- `client/src/features/accounting/LasikRevenue.tsx:172,404,421`, in report labels and missing-value fallbacks.

The rule forbids em dashes in UI text written by the agent. The same character is currently used both as prose punctuation and as a data placeholder, so the violations are distributed rather than isolated.

**Why it matters:** This creates an inconsistent copy contract and makes an otherwise real record indistinguishable from decorative punctuation or an absent value.

**Suggested fix after approval:** Replace prose em dashes with punctuation accepted by R-02. Replace missing-value dashes with an explicit Arabic label such as `غير متاح` or an empty value where the field context already communicates absence. Audit all accounting-visible strings, not only the examples above.

### 2. HIGH — Accounting home summary errors have no rendered recovery action

**Rule:** R-27, UI States, Hard Gate

**Evidence:** `client/src/features/accounting/AccountingHome.tsx:289-294` defines `hasSummaryError` and `refreshSummary`, but the search shows no rendered use of either value. The surrounding UI does not render a summary-level alert or retry control. `client/src/features/accounting/AccountingShell.tsx:143-167` reduces failed summary metrics to the text `تعذر التحميل`, with no action attached to recover them.

The activity feed has its own retry branch at `AccountingHome.tsx:783-793`, but the shell-level revenue, receipt-count, and cashbook-balance metrics are a separate data surface and are left without an action.

**Why it matters:** A user can see that the financial pulse failed but cannot refresh it from the screen. R-27 requires an error state that identifies the failure and provides the available next action; this is particularly important for an accounting landing surface.

**Suggested fix after approval:** Render one compact summary error state with a labelled retry action, or provide per-metric recovery where data sources differ. Keep stale values out of the failed state unless they are explicitly labelled as stale.

### 3. HIGH — Cashbook empty state does not distinguish first use from filtered results

**Rule:** R-27, UI States, Hard Gate; C-4, Resilience

**Evidence:** `client/src/features/accounting/AccountingCashbook.tsx:271-274`, `304-307`, and `493-497` repeat only `لا توجد حركات` for the empty state across mobile and desktop render paths. The screen supports year, transaction-type, and notes filters at `AccountingCashbook.tsx:166-245`, but the empty message does not say whether the ledger is genuinely empty, whether the current filters removed every result, or what action the user should take next.

**Why it matters:** The same message describes multiple materially different states: first use, no records for a selected year/type, and a search with no match. The user cannot decide whether to add a ledger entry, reset filters, or widen the period.

**Suggested fix after approval:** Split the state by cause. For filtered-empty results, show the active filter context and a reset-filters action. For first use, explain that no entries exist and link or focus the supported add-entry action. Keep the mobile and desktop messages semantically identical.

### 4. HIGH — Expense pagination controls are icon-only without accessible names

**Rule:** R-26, Interactive Elements, Hard Gate; R-32, Keyboard and Focus, Hard Gate

**Evidence:** `client/src/features/accounting/AccountingExpenses.tsx:28` renders the previous and next pagination controls as raw `<button>` elements containing only `<ChevronRight>` and `<ChevronLeft>`. Neither button has `aria-label`, visible text, or a title. The same screen has labelled controls in other areas, so this is a localized regression rather than a missing component capability.

**Why it matters:** Screen-reader users receive unnamed buttons, and a keyboard user cannot infer which direction each control moves. The icons also change meaning in RTL layouts unless the accessible name states the action explicitly.

**Suggested fix after approval:** Add Arabic accessible names such as `الصفحة السابقة` and `الصفحة التالية`, preserve the existing disabled states, and verify the focus indicator remains visible in both themes.

### 5. LOW — The accounting home does not perform the job described in its own product brief

**Rules:** C-3, Content-Driven Composition; R-20, Generic Design, Quality Lock; R-05, Structure and Rhythm, Quality Lock

**Evidence:** The brief in `.claude/plans/accounting-home-shape-brief.md:7-9` defines `/accounting` as a launchpad: glance at financial pulse, then navigate to the right report. The layout specification at lines 30-40 calls for a metric ribbon, activity feed, and report shortcut list, and explicitly says the home page should have no forms.

The current `client/src/features/accounting/AccountingHome.tsx:361-367` instead puts three write workflows, `قيد خزنة`, `خدمة`, and `قرض`, ahead of the activity feed. The only links found in the home screen are receipt-detail links at `AccountingHome.tsx:825-826` and `1129-1136`; the planned report shortcut list and four clickable KPI metrics are not rendered. The file also retains two large inactive legacy blocks guarded by `false &&` at `AccountingHome.tsx:368` and `496`, which makes the current composition harder to reason about.

**Why it matters:** The first screen asks users to choose an entry form before it helps them reconcile or navigate. That reverses the documented accounting task hierarchy and makes the page feel like a generic dashboard-plus-form rather than a focused operational hub.

**Suggested fix after approval:** Choose one product role and make it explicit. For the documented launchpad role, move write actions to their dedicated routes or a deliberate secondary action, restore the sourced metric ribbon and report list, keep the activity feed dominant, and remove the inactive legacy branches. If the product intentionally changed to an entry workspace, update the brief and re-derive the hierarchy from that new job.

### 6. LOW — Repeated nested cards, 28px corners, and soft shadows flatten hierarchy

**Rules:** R-11, Radius; R-12, Elevation; C-1, Intentionality, Quality Locks

**Evidence:** The project direction says new cards use at most 8px radius and that cards should frame actual repeated items or tools without nested-card stacking (`DESIGN.md:70-77`). The accounting module repeatedly exceeds that dose:

- `client/src/features/accounting/AccountingCashbook.tsx:250` uses `rounded-[28px] shadow-sm` for the history surface, then uses `rounded-2xl shadow-sm` for each mobile row at `AccountingCashbook.tsx:310-316`.
- `client/src/features/accounting/AccountingHome.tsx:761` wraps activity in `rounded-2xl`, then each mobile receipt row uses another rounded, shadowed surface at `AccountingHome.tsx:815-822`, with additional rounded metric blocks at `850-882`.
- `client/src/features/accounting/PatientAccount.tsx:248-296` places six rounded, shadowed summary blocks inside a Card, and its receipt rows repeat the same pattern at `299-342`.
- `client/src/features/accounting/AccountingExpenses.tsx:26-27` uses the same oversized `rounded-[28px] shadow-sm` history treatment.

**Why it matters:** The active record, table container, row, and metric field all receive the same elevated visual treatment. In dense financial work, this makes hierarchy less scannable and turns radius/shadow into decoration rather than a state or grouping signal.

**Suggested fix after approval:** Use the shared radius scale consistently, reserve elevation for the one surface that genuinely needs separation, and replace nested cards with unframed groups or table rows where the surrounding section already provides containment. Keep the mobile key-value transformation, but let its rows use borders and spacing rather than multiple floating surfaces.

## Delivery-gate status

The six approved findings were implemented after the audit. The focused tests, TypeScript check, and production build pass. This still does **not** certify every accounting route as visually verified because the following Delivery Gate evidence was not run in this task:

- Runtime click-through of every accounting control.
- Browser console inspection across accounting routes.
- Measured contrast for every visible text/state combination in both themes.
- Desktop and mobile visual inspection of every accounting route, including print routes.
- Full keyboard traversal and Escape/focus restoration for every drawer and dialog.

## Resolution

All six findings were approved and addressed:

1. Removed em dashes from accounting-visible copy and replaced missing-value placeholders with explicit text.
2. Added a rendered accounting-home summary error state with a labelled retry action.
3. Split cashbook empty states into filtered-empty and first-use states, with reset or first-entry actions.
4. Added accessible names, titles, focus styles, and 44px touch targets to expense pagination controls.
5. Rebuilt the accounting home as a launchpad with sourced metrics, activity, report links, and secondary admin sync actions instead of write-first forms.
6. Reduced oversized radii, repeated shadows, and nested floating-card treatment across the audited accounting surfaces.

No commit or server restart was performed.
